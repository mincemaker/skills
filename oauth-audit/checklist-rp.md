# OAuth / OIDC RPライブラリの監査チェックリスト

[oauth-redirect-attacks](https://github.com/mincemaker/oauth-redirect-attacks/blob/b001ca62035d9f11bdbdb6331207431d6db728d0/README.md#7-チェックリスト) `b001ca6` の第7節の「クライアントに送るもの」を、SSOライブラリにテストを書ける形に整理したもの。RPの番号は原文の掲載順。ケース名は監査テストのサブテスト名にそのまま使う。

各項目には、守りたいものと、それを破る攻撃の出典を書いた。攻撃の手順と前提は、`sources/zenn/` の章と原文の README の節にある。判定と出し方は SKILL.md の「5. 判定する」に従う。

## 判定の単位

ライブラリ全体ではなく、プロバイダごとに判定する。同じライブラリでも、PKCEやIDトークンの扱いはプロバイダごとに違うことが多い。

対象がライブラリではなくアプリそのものなら、IdPごとに判定し、アプリ委任の区分は使わない。ドキュメントではなく実装で判定する。

## 判定の区分

| 判定 | 使う条件 |
|---|---|
| 適合 | 守りたいものを破る攻撃が、ライブラリの範囲で止まる |
| アプリ委任 | ライブラリは攻撃を止めないが、アプリが止めるべきことをドキュメントに書いている。該当箇所へのリンクを付ける |
| 不適合 | 攻撃が成り立ち、アプリへの委任もドキュメントに無い。テストで攻撃を再現したか、攻撃の決め手になる1歩を示した |
| 未確認 | テストでもソースでも確かめられない範囲が残る。残った範囲を書く |
| 対象外 | 攻撃の前提になる機能が無く、攻撃を組めない。例として、IDトークンを扱わないOAuth 2.0だけのプロバイダのRP-07〜10。理由を書く |

アプリ委任は原文に無い区分で、ライブラリを監査するときの読み替え。原文はアプリの診断を前提にしているので、ライブラリが止めない攻撃は、それを使うアプリが止めることになる。アプリが止めるべきことをドキュメントが伝えていなければ、アプリの作者は気づけないので不適合とする。例えば、セッションを扱わないライブラリのREADMEに、ログイン後にセッションIDを更新するよう書かれていなければ、RP-03は不適合。RP-01とRP-03はアカウントとセッションの設計に依存するので、ライブラリが扱わないならアプリ委任か不適合のどちらかになる。

表のケースは攻撃を確かめる代表例で、すべてを尽くしてはいない。表に無い `extra_` のケースで攻撃が成り立つことを示したら、その項目を不適合とする。

## テストの仕掛け

本物のIdPには接続しない。偽のIdPには `tools/fakeidp` を使い、ライブラリの外向きの通信をすべてそこへ向ける。使い方は SKILL.md の「RPの偽のIdP」にある。

- 外向きの通信の差し替え: JavaScriptなら `fetch` を包んでオリジンを差し替える。Pythonならrespxなどで転送する。どのURLに何を送ったかは偽のIdPの `/_audit/requests` で読む。
- 偽のIdPが持つもの。`fakeidp` が使えずテスト内に書くときも、これを揃える
  - codeとユーザーの対応。codeには、発行時の `code_challenge` と `redirect_uri` を結び付ける
  - トークンエンドポイント。PKCEを検証し、IDトークンを返すときはテスト用の鍵で署名する
  - UserInfoとJWKS。プロバイダが使うものだけ
  - 応答の改ざん。iss、aud、exp、nonce、sub、署名などをケースごとに変える
- ライブラリを組み込んだ最小のアプリを、テスト内の別関数で用意する。ログインの開始とcallbackのURLだけを持ち、ログインが成立したらユーザーIDを返す。
- ブラウザの代わりに、Cookieを保持するテスト用のクライアントを二つ用意する。被害者のブラウザと攻撃者のブラウザ。

各ケースで記録するもの:

- ログインが成立したか。成立したなら、誰として成立したか
- トークンエンドポイントへ要求を送ったか。送ったなら、送り先と中身
- ライブラリが返したエラー

画面にログイン失敗と出ただけで、攻撃が止まったと判定しない。code やトークンがどこへ送られたか、誰としてログインしたかで判定する。

## テストの共通ルール

- 対象のテスト基盤と既存の補助関数を使う。ライブラリのコードは変えない。
- 既定のcallbackは `https://app.example/callback`、偽のIdPのissuerは `https://idp.example`。

## IdP側の不備

本物の IdP を使う設定で、IdP 側の不備に気づいたら、ライブラリの判定とは分けて「IdP の不備」として書く。原文の README の第0節。偽のIdPを使うテストでは起きないが、ライブラリが IdP の挙動を前提にしているときに出る。

## RP-02: stateの欠落・改ざん・別セッションの値を検出する

守りたいもの: state で CSRF を防ぐクライアントで、攻撃者が用意した callback の URL を被害者に踏ませても、ログインや連携が完了しないこと。攻撃は `sources/zenn/07-csrf.txt`。

| ケース | callbackに送るもの | 期待 |
|---|---|---|
| state_valid | 自分のフローのstate | ログイン成立 |
| state_missing | stateを削除 | 拒否。トークン要求を送らない |
| state_tampered | 1文字変えたstate | 拒否。トークン要求を送らない |
| state_other_session | 攻撃者のブラウザで得たstateを、被害者のCookieと一緒に送る | 拒否。トークン要求を送らない |
| state_replay | 成功したcallbackを、同じブラウザからもう一度送る。ブラウザはcallbackの応答の Set-Cookie に従い、削除されたCookieは送らない | トークン要求を送らない。偽のIdPがcodeの再利用を拒否するので、ログインの失敗では判定しない |
| extra_state_replay_same_cookies | callbackの直前のCookieを写しておき、それで同じcallbackを送る | 記録する。Cookieだけでstateを持つ設計では通る |
| state_cookie_attributes | ログイン開始時のSet-Cookie | 記録する。HttpOnly、Secure、SameSite、有効期限、Path |

state ではなく PKCE や nonce で CSRF を防ぐ設計なら、state_missing が通っても攻撃は止まるので不備ではない。RP-05 と RP-01 の結果で判定する。

`response_mode=form_post` を使うクライアントでは、認可サーバからのクロスサイトの POST で callback が呼ばれるので、SameSite=Lax のセッション Cookie は送られない。この都合で state の照合を外していないかを、state を改ざんした POST で確かめる。原文の README の第5節。

対象がstateを発行しないなら、次のように置き換え、置き換えたことを報告に書く。

- state_missing: そのまま流し、受理することを記録する。守る値が無いことは RP-04 と RP-05 で判定する
- state_tampered: 任意の値を付けて送る
- state_other_session: 攻撃者のブラウザの認可レスポンスを、そのまま被害者のCookieで送る
- state_cookie_attributes: セッションのCookieの属性を代わりに記録する
- RP-04 の entropy: 乱数で作る値が無いことを、認可URLのパラメータで確かめる

## RP-04: state・nonce・verifierをフローごとに生成する

守りたいもの: state、nonce、verifier を攻撃者が予測したり、別のフローの値を使い回したりできないこと。値が固定か使い回しなら、どの防御も効かない。RFC 9700 §2.1.1 は、これらの値をフローごとに作り、フローを始めたクライアントとブラウザに結び付けるよう求めている。

| ケース | 手順 | 期待 |
|---|---|---|
| fresh_per_flow | ログインを2回始める | state、nonce、code_verifierが毎回違う |
| entropy | 生成元をソースで確かめる | 暗号学的乱数で、128ビット以上 |
| app_supplied_value | アプリが値を渡せるオプションがあるか | 記録する。固定値を渡せるなら、ドキュメントに注意があるか |

state、nonce、verifier のどれも使わない対象は、守る値が無いので対象外ではなく不適合とし、RP-02 や RP-05 と同じ原因であることを書く。

## RP-05: 別ブラウザのcodeを注入されても他人にならない

守りたいもの: 被害者の code を盗んだ攻撃者が、自分のブラウザのフローに code を差し替えて送っても、被害者としてログインできないこと。攻撃は `sources/zenn/05-authorization-code-injection.txt` と原文の README の第3節。RP-01のアカウント紐付けの前提にもなる。

| ケース | 手順 | 期待 |
|---|---|---|
| code_injection | 1. 被害者のブラウザでログインを始め、stateを得る。2. 攻撃者のブラウザで自分のフローを進め、callbackに届く前のcodeを取り出す。3. 被害者のブラウザで、被害者のstateと攻撃者のcodeをcallbackに送る | 拒否。成立すると、被害者のセッションが攻撃者として扱われる |

state の照合では止まらない。攻撃者は自分のセッションの state を使うので、照合は通る。止めるのは PKCE か nonce で、client secret などのクライアント認証も止めない。トークン要求を送るのは正規のクライアントだからである。nonce で止めてよいのは confidential な OIDC クライアントに限られる。

PKCE を使うクライアントで注入が通ったら、IdP の不備と決める前に、クライアントが verifier をフロー間で使い回していないかを確かめる。使い回していれば、IdP が正しく照合しても通る。

## RP-06: public clientがPKCEを使い、方式をS256にする

守りたいもの: public client の漏れた code を、攻撃者がトークンエンドポイントへ直接送って使えないこと。public client には secret が無いので、PKCE が無ければ漏れた code はそのままアクセストークンになる。原文の README の第3節。

| ケース | 見るもの | 期待 |
|---|---|---|
| pkce_sent | 認可リクエストのURL | `code_challenge` がある |
| pkce_s256 | 同じURL | `code_challenge_method=S256` |
| pkce_verifier_sent | トークン要求 | `code_verifier` を送り、challengeと対応する |

判定: public clientでPKCEが無いか、方式が `plain` なら不適合。`plain` は verifier をそのまま認可リクエストに載せるので、認可リクエストを読める攻撃者には効かない。confidential clientでPKCEが無い場合は、RP-05の code_injection がnonceなど別の手段で止まれば適合、止まらなければ不適合とし、RP-05と同じ原因であることを書く。confidential client が `plain` を使うなら、RFC 9700 §2.1.1 の S256 の SHOULD に反するので info に出す。

## RP-07〜RP-10: IDトークンとUserInfo

守りたいもの: 注入された code や書き換えた ID トークンで、別人としてログインさせないこと。認可コードフローの ID トークンはトークンエンドポイントから裏の通信で届くので、ブラウザでは書き換えられない。各項目だけを変えた署名の正しい ID トークンを、偽のIdPで出して確かめる。原文の README の第6節。

前提: プロバイダがIDトークンを受け取る。受け取っても使わず捨てるなら、ライブラリが未検証のIDトークンやそのクレームをアプリに渡していないかを確かめる。渡していれば、アプリがそれを信じて別人としてログインさせうるので不適合とし、渡していなければ対象外にする。未検証のIDトークンを、文字列のままでもクレームでも、公開のAPI (プロパティや戻り値) で取り出せるなら「渡している」とみなす。

| ケース | 偽のIdPが返すIDトークン | 期待 | 項目 |
|---|---|---|---|
| idt_valid | 正しいもの | ログイン成立 | |
| idt_nonce_mismatch | nonceが違う | 拒否 | RP-07 |
| idt_nonce_missing | 認可リクエストでnonceを送ったのに、IDトークンにnonceが無い | 拒否。nonceを送らないプロバイダでは対象外 | RP-07 |
| idt_token_unused_before_nonce | nonceが違う場合に、アクセストークンでUserInfoなどを呼んだか | 呼ばない | RP-07 |
| idt_iss_mismatch | issが別 | 拒否 | RP-08 |
| idt_aud_mismatch | audが別のclient_id | 拒否 | RP-08 |
| idt_aud_untrusted_extra | audに自分と信頼しない値の両方 | 拒否。`azp` の扱いも記録する | RP-08 |
| idt_expired | expが過去 | 拒否 | RP-08 |
| idt_bad_signature | 署名を壊す | 認可レスポンスで受け取るIDトークンなら拒否。トークンエンドポイントから直接受け取るなら、署名検証を TLS で代えてよいので記録する | RP-09 |
| idt_alg_none | `alg: none` | 拒否 | RP-09 |
| userinfo_sub_mismatch | UserInfoのsubがIDトークンと違う | 拒否 | RP-10 |

RP-07: nonce で注入を防ぐなら、照合で拒否しても、その前にアクセストークンを使って連携やプロフィールの取得を済ませていれば注入は通っている。認可レスポンスにも ID トークンが入る構成 (`response_type=code id_token`) で、そちらだけを照合していないかも見る。nonce は1回限りの値なので、照合に使い終えた nonce をセッションから消しているかをソースで確かめる。消していなくても攻撃を示せなければ、RFC 9700 §4.5.3.2 に沿っていないので info に出す。

RP-10: UserInfo の応答が ID トークンの利用者のものとは限らないので、OIDC Core §5.3.2 は sub の照合を MUST としている。偽のIdPで UserInfo の sub をずらして、別人としてログインするかで判定する。

## RP-11: callbackのページやログからcodeを漏らさない

守りたいもの: callback の URL に載った code を、Referer、外部スクリプト、ログから外へ漏らさないこと。漏れた code は RP-05 の注入に使われる。攻撃は `sources/zenn/03-credential-leakage-via-referer-headers.txt` と原文の README の第5節。外部のスクリプトは Referer を介さず `location.href` から code を読める。

| ケース | 手順 | 期待 |
|---|---|---|
| callback_strips_code | 成功したcallbackの応答を見る | codeを除いたURLへ転送する。ライブラリがアプリに処理を渡すなら、そのときのURLとドキュメントを記録する |
| log_no_code_or_token | ログイン1回分のログ出力を集める | codeもトークンも含まない |
| error_no_token | トークン要求やリソースの取得を失敗させ、エラーの応答とログを見る | codeもトークンも含まない |

ライブラリの範囲で確かめる。

- callbackの処理の後、codeを含むURLのままページを描画するか、codeを除いたURLへ転送するか。
- エラーのメッセージや例外、ログにcode、state、トークンを入れるか。ソースで確かめる。
- ライブラリがcallbackのページを自分で描画するなら、そのページのReferrer-Policyが既定より緩くないか、外部リンク・外部リソース・外部スクリプトが無いか。
- 転送先のページのReferrer-Policyや外部リソースは、アプリ委任として扱う。

判定: ライブラリがcallbackを処理したあと、codeを含むURLのままアプリの処理に渡すなら、codeを除いたURLへ転送するか、転送すべきことをドキュメントに書いていれば適合。どちらも無ければ不適合。ログやエラーにcodeやトークンを出すなら、それだけで不適合。ライブラリ自身はログを書かなくても、codeやトークンを含む例外を投げ、ドキュメントの使用例のままのフレームワークの既定のエラー処理がそれをログに出すなら、不適合とする。既定の Referrer Policy のままで外部リソースがあるだけなら、info に出す (RFC 9700 §4.2.4 の SHOULD NOT)。

## RP-12: アクセストークンをURLのクエリに載せない

守りたいもの: アクセストークンを、ブラウザの履歴やサーバのログに残さないこと。クエリに載ったトークンは、履歴やアクセスログから漏れて不正に使われる。攻撃は `sources/zenn/04-credential-leakage-via-browser-history.txt` と原文の README の第5節。

| ケース | 見るもの | 期待 |
|---|---|---|
| token_not_in_query | ライブラリの公開APIが行うすべての外向きの要求のURL。ログインの流れの外にある関数、例えばトークンの失効や更新も含む | アクセストークンやリフレッシュトークンを含まない。Authorizationヘッダーか本文で送る |

ログインの流れで送らず、失効などの関数だけがクエリに載せる場合も不適合とし、どの関数かを書く。

## RP-13〜RP-15: mix-up攻撃

守りたいもの: 複数の IdP を使うクライアントで、攻撃者の IdP を選んで始めたフローに正規の IdP の code が届いても、その code を攻撃者の IdP へ送らないこと。攻撃は `sources/zenn/11-mixup-attack.txt` と原文の README の第5節。

前提: アプリが複数のIdPを併用できる。IdPが1つしか使えない対象では、RP-13〜15をすべて対象外にしてスキップする。RP-14は、IdPが `iss` パラメータに対応する場合に限る。

| ケース | 手順 | 期待 | 項目 |
|---|---|---|---|
| mixup_defense | どの対策を使うかをソースで確かめる。iss、IDトークンのiss、IdPごとのcallback | 1つ以上あり、実際に効いている。IdPごとのcallbackがあっても cross_callback で突破されるなら不適合 | RP-13 |
| iss_mismatch | 認可レスポンスの `iss` を別の値にする | トークン要求を送らずに止まる | RP-14 |
| iss_missing | IdPのメタデータが `authorization_response_iss_parameter_supported: true` のとき、`iss` を削除する | トークン要求を送らずに止まる | RP-14 |
| cross_callback | 同じアプリにプロバイダAとBを組み込み、Aで始めたフローの認可レスポンスをB用のcallbackに送る | IdPごとのcallbackで防ぐ設計なら、トークン要求を送らずに止まる。issで防ぐ設計なら記録する。stateのCookie名が共有されていないかも記録する | RP-15 |

iss はトークン要求を送る前に確かめる必要がある。トークンレスポンスの ID トークンの iss で確かめても、code はもう送った後になる。トークン要求がどこへ送られたかで判定する。

IdP ごとに callback を分けるだけの対策は、攻撃者が正規の IdP に自分の client を登録し、その redirect URI に被害クライアントの別の IdP 用の URI を使うと突破される。この対策だけなら、攻撃を示せなくても iss の照合を勧める所見として書く。

RP-14の前提は、本物のIdPが `iss` パラメータに対応しているかで決まる。本物のIdPに接続できず前提を確かめられなければ、偽のIdPで `iss_param` を有効にして iss_mismatch と iss_missing を試し、ライブラリの挙動を記録したうえで未確認とする。確かめられなかった前提を、残った範囲として書く。

## RP-16: Implicit Grantを使わない

守りたいもの: 攻撃者が自分のフローの認可レスポンスのアクセストークンを、被害者から盗んだものに差し替えても、被害者としてログインさせないこと。Implicit ではトークンがフローにも利用者にも結び付かないので、state では止まらない。攻撃は `sources/zenn/06-at-injection.txt` と原文の README の第6節。

| ケース | 見るもの | 期待 |
|---|---|---|
| response_type_code | 認可リクエストの `response_type` | `code`。`token` を含むなら、nonceと `at_hash` の照合をRP-07〜08と同じ形で試す |
| token_substitution | `token` を含む場合だけ。被害者のフローの認可レスポンスのアクセストークンを、攻撃者のものに差し替えて送る | 拒否。成立すると、攻撃者のユーザーとしてログインできる |

Implicit を使っても差し替えが止まるなら不適合にしない。Implicit を使うこと自体は RFC 10017 §7.2 の MUST NOT に反するので info に出す。

## RP-01とRP-03

守りたいもの: 攻撃者の code で、被害者のアカウントに攻撃者の外部アカウントが紐付かないこと (RP-01)。state、nonce、verifier の防御の前提になるセッションを、攻撃者が固定できないこと (RP-03)。攻撃は `sources/zenn/07-csrf.txt` と、その章の脚注にあるセッションの前提。

| ケース | 手順 | 期待 |
|---|---|---|
| code_injection_no_flow | 被害者のブラウザではフローを始めず、攻撃者が自分のフローで得たcodeとstateを、被害者のブラウザからcallbackに送る | 拒否。トークン要求を送らない |
| session_rotation_after_callback | ログイン開始の前とcallbackの後で、セッションのCookieの値を比べる。ライブラリがセッションを扱わなければスキップし、ドキュメントで判定する | 値が変わる |

RP-03 の攻撃は、攻撃者が被害者のブラウザにセッションの Cookie を植えられることを前提にする。植える手段が対象の外にあっても、それは攻撃者の能力の前提なので、ログインの後にセッションを更新しなければ不適合とする。

被害者がフローを始めた状態での注入は、RP-05の code_injection で試す。PKCE だけで防ぐクライアントへの攻撃は、被害者のセッションに verifier が残っている、フローを始めた状態で成り立つ。

RP-01 の報告には、判定の根拠を分けて書く。code_injection と code_injection_no_flow のテストの結果と、アカウント紐付けについてのドキュメントの有無である。テストで止まっても、ライブラリが紐付けを扱わずドキュメントにも注意が無ければ不適合とし、そのことを書く。

| ID | ライブラリで確かめること |
|---|---|
| RP-01 | ログイン成立後、既存のセッションやアカウントへの紐付けをライブラリが行うか。行わないなら、アプリが紐付け前に確かめるべきことがドキュメントにあるか |
| RP-03 | ログインの開始時とcallbackの後に、ライブラリがセッションIDを発行・更新するか。しないなら、ドキュメントに書いてあるか |
